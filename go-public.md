# Go Public: Paintings That Listen

## The idea

This should not be “an Instagram for screensavers.” It should be a gallery of **slow visual music objects**: minimal audiovisual works that listen to sound and respond with restraint.

Think of them as moving paintings—full-screen, abstract, ambient, and slightly strange. Less equalizer, more living painting. In a digital world full of aggressive visuals, this project offers screens that breathe.

The account is a public-facing art project first. The software and product opportunities can emerge from the desire the work creates.

## Visual identity

The feed should feel like a small digital gallery:

- Dark backgrounds and generous negative space.
- Very little text; let the visuals speak.
- 10–20 second loops as the basic unit.
- Each work receives a title, mood, and sound pairing.
- A palette of black, cream, deep red, smoke blue, ochre, violet, and grey.

Avoid loud gradients, obvious AI gloss, neon cyber soup, busy typography, stock footage, and captions that cover the visual. The work should feel deliberate, painterly, and calm.

Use language with warmth and specificity. Avoid startup phrasing such as “revolutionising visualisation” or “AI-powered immersive experiences.” Prefer descriptions like:

- “A field of red responding to low piano.”
- “Bass expands the colour. Treble wakes the grain.”
- “Made with WebGL. Best viewed full screen.”
- “For ambient music, sleep rooms, and laptops left open at midnight.”

## Post formats

Use a vertical 9:16 composition with the visual full screen. Add no text, or only a small title at the bottom.


or:


### Carousels

A strong carousel structure is:

1. Final visual still.
2. One-sentence description.
3. Audio mapping.
4. Colour palette.
5. A code fragment.
6. An invitation to try it.

Example: **Study 02: Living Ink Wash** — an ink field responding to piano; bass creates blooms, treble feathers the edge, and silence lets the ink dissolve.

- Should bass move colour or shape?
- Would you use this as a screensaver?

## Automatic publishing with the Meta API

Once the visual studies are being produced consistently, the account can publish them automatically to a Facebook Page and a linked Instagram Professional account. The safest model is to keep a small content calendar in our own system, then have a scheduled worker publish approved assets at the chosen time.

### What the system should do

Each content item can contain:

- The finished video, still image, or carousel assets.
- A title and caption.
- The target channels: Instagram, Facebook, or both.
- The format: Reel, image post, carousel, or link post.
- A planned publication time.
- A status such as draft, approved, publishing, published, or failed.
- The returned Meta post IDs and public URLs.

The workflow should be:

1. Generate or upload the visual asset to durable storage.
2. Create a draft post with its caption and channel settings.
3. Approve the post manually during the initial launch phase.
4. At the scheduled time, publish it through Meta’s Graph API.
5. Record the response IDs, publication time, and any error.
6. Retry transient failures without ever publishing the same item twice.

### Meta setup

Create a Meta developer app and connect:

1. A Facebook Page for the project.
2. An Instagram Professional account linked to that Page.
3. The required publishing permissions and a long-lived access-token flow.
4. App Review and Business Verification when required for production use.

The exact permission names and requirements can change with Meta’s API versions, so implementation should use the current [Instagram Content Publishing documentation](https://developers.facebook.com/docs/instagram-api/guides/content-publishing/), [Facebook Pages publishing documentation](https://developers.facebook.com/docs/pages-api/posts/), and Meta’s [official Instagram API collection](https://www.postman.com/meta/instagram/documentation/6yqw8pt/instagram-api).

Never put the App Secret or Page access token in frontend code, rendered media, captions, or a public repository. Store them as server-side secrets and rotate them when needed.

### Instagram publishing flow

For a Reel, the backend should use Meta’s container-based flow:

1. Host the finished MP4 at a temporary, publicly reachable HTTPS URL. Meta must be able to fetch the file; a local filesystem path will not work.
2. Create an Instagram media container for the Instagram user, specifying `media_type=REELS`, the `video_url`, and the caption.
3. Poll the container until Meta reports that processing is finished.
4. Publish the container with `/{ig-user-id}/media_publish` and its `creation_id`.
5. Save the returned media ID and permalink.

For a still or carousel, create the appropriate image containers first, then publish the parent container. Keep the generated media in storage even after publishing so that a failed job can be retried and the original post can be audited.

### Playwright capture pipeline

Playwright can turn the browser visualiser into a repeatable content studio. Instead of manually screen-recording a session, a capture job can open the visualiser, load a selected audio track, hide the controls, record a fixed-duration session, and hand the resulting asset to the Meta publisher.

The flow should be:

1. Start a local or preview HTTP server for `Resources/index.html` so the page has a normal origin.
2. Launch Playwright with a fixed viewport, device scale factor, colour scheme, and browser version.
3. Open the visualiser and wait for the WebGL canvas to be ready.
4. Load the selected audio file through the existing file input, or use a deterministic scripted audio source for repeatable studies.
5. Hide the controls with the page’s `H` shortcut and optionally enter fullscreen.
6. Record the session for a defined duration, such as 15 seconds.
7. Save a thumbnail and the recorded video with a stable content ID.
8. Convert the recording to a broadly compatible MP4 if necessary, then upload it to public HTTPS storage.
9. Create the Instagram and Facebook post jobs, leaving them in `approved` status until a human reviews the result.

Playwright’s video recording captures the browser viewport. It should be treated as the visual capture layer, not as the publishing layer. If the post needs the original music, keep the audio file separately and mux it into the rendered video with FFmpeg before publishing. This avoids relying on browser/system-audio capture, which is less portable and harder to reproduce in a worker.

A minimal capture script could look like this:

```js
import { chromium } from "playwright";

const browser = await chromium.launch();
const context = await browser.newContext({
  viewport: { width: 1080, height: 1920 },
  deviceScaleFactor: 1,
  recordVideo: { dir: "captures" }
});

const page = await context.newPage();
await page.goto("http://127.0.0.1:4173/Resources/index.html");
await page.locator("#file").setInputFiles("audio/study-01.mp3");
await page.waitForTimeout(1500);
await page.keyboard.press("h");
await page.waitForTimeout(15000);

const video = page.video();
await page.close();
const rawPath = await video.path();
await context.close();
await browser.close();

console.log(`Captured ${rawPath}`);
```

In production, the capture worker should also verify that the canvas is non-blank, use a timeout around page and media readiness, clean up temporary files, and record the exact visualiser version, audio track, viewport, and shader parameters alongside the asset. That metadata makes it possible to reproduce a popular study later.

The capture service should not log into Facebook or Instagram through Playwright. Use Playwright for the controlled browser session and the official Meta Graph API for publishing. This keeps credentials out of the browser, avoids brittle UI automation, and gives us post IDs, error responses, and idempotent retries.

### Facebook publishing flow

For the Facebook Page, use the Page publishing endpoints appropriate to the asset:

- Text or link post: `POST /{page-id}/feed`.
- Image post: `POST /{page-id}/photos` with a public image URL or uploaded media.
- Video post: the Page video publishing flow.

Facebook Page posts can support scheduled publication where the current API permits it. For consistency across Facebook and Instagram, our own scheduler should remain the source of truth and publish each channel independently. That gives us one calendar, one approval process, and clear recovery when only one channel succeeds.

### Recommended first implementation

Start with a small private publishing service rather than a fully automatic public bot:

- A `content` table or JSON-backed queue for the editorial calendar.
- An object-storage bucket for MP4s, thumbnails, and carousel images.
- A scheduled job that runs every few minutes.
- One Meta adapter for Instagram and one for Facebook.
- An approval flag before any post can go live.
- An idempotency key per channel and content item.
- Structured logs, failure alerts, and a simple publish history page.

The first version can publish the first twelve posts from this document, including the Reel loops, process carousels, manifesto text, polls prepared for manual Stories, and the prototype invitation. Polls and some interactive Story formats may still need to be posted manually depending on the account type and the current API capabilities.

### Editorial guardrails

Automation should handle repetition, not taste. Keep a human approval step until the visual language and cadence are proven. The system should also prevent duplicate captions, skip missing media, validate aspect ratios and file sizes before upload, and stop after repeated API errors rather than flooding Meta with retries.

The goal is a quiet publishing machine behind a quiet art project: reliable enough to maintain the rhythm, invisible enough not to become the personality.
